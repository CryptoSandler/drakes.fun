# Round: the three-batch session of 2026-09-01

CLAUDE.md asks for an adversarial round before a change to the data model, the
program, or a product decision, and asks for three things by name. Two of these
three batches qualify: the site batch adds the first migration and makes a
product claim, and the hosting batch spends money on the owner's behalf.

The owner asked for the batches to be sequenced without stopping, so this round
is written alongside the work rather than before it, and it says which of its
findings changed the implementation. That is a deviation from the letter of the
rule and it is recorded here rather than glossed.

---

## 1. The strongest case AGAINST

### Against the chain-reading verifier

*"You are gold-plating a tool nobody runs. The verify page's audience is a
handful of sceptics, the artifacts are ours to keep, and the actual fix for
2026-09-01 is one line of operational discipline — do not delete published
artifacts. You have written a paginated event indexer to solve a filing
problem."*

**This is partly right, and it is the reason the offline `pieces <dir>` was
kept rather than deleted.** Where it fails is the audience: the artifacts are
served from a host we control, so a reader who checks the permutation against
our files has verified our arithmetic against our arithmetic. That is not a
weaker version of the claim, it is a different claim. The chain read is what
makes the sentence on the README true.

And the discipline argument is refuted by the incident itself. The artifacts
were not deleted carelessly; they were deleted, and the tool then reported
**0 of 49 matching** — a total mismatch. The failure mode is not "we lose a
file", it is "losing a file is indistinguishable from a defect in the
protocol", and no amount of care removes that.

### Against building the crank host now

*"There is no mainnet mint, no pool, and no launch date. B3 has not run. You are
choosing a host for a job that will not exist for weeks, using prices that will
have changed, and the crank you productionised will be rewritten when the
survivor selection and the artifact publishing change."*

**Substantially right about timing, wrong about order.** The prices will move
and the document says so. What will not move is the finding: an hourly cranker
does not fit the plan we already pay for, and discovering that at launch is
discovering it at the worst moment. The evaluation is cheap now and expensive
later.

The rewrite risk is real and is why `issue.ts` holds no state.

### Against the site batch

*"A page that shows one issuance is not a product. B6 is the site batch and it
is behind B5 for a reason. You are adding Next, React, a Postgres schema, a
migration runner and a Neon dependency to render eleven rows that a block
explorer already shows better."*

**The strongest of the three, and it should be conceded in part.** Eleven rows
is not a product and this page is not defended as one.

What the batch actually buys is the infrastructure D14 deferred out of B0 with
the explicit reason that *"a migration runner that has never been run against a
Postgres instance is unverified code"*. That runner is now run, twice, against
two real databases, and its guards have been made to fail on purpose. The page
is the thing that proves the reads work; it is not the thing being delivered.

**The part not conceded:** the block explorer does not show the recipient was
*derived*. That is the whole claim.

## 2. The collision with the real code

What the repository already knew that the request did not:

1. **There is no reserve, and there cannot be one yet.** The request asks the
   page to show "reserva actual en PUMP". The reserve PDA, `claim_fees` and
   `redeem` are the **Phase 2** program (B9, D8). The Phase 1 program *holds
   nothing, and that is precisely what makes it deployable before an audit*.
   There is also no `$DRAKES` mint and no pool, because B3 has not run, so
   there are no fees to accumulate.

   **Handled as a decision with a door** (CLAUDE.md): the mechanism reads a
   named address' `$PUMP` balance at a slot and works unchanged in Phase 2; the
   configuration is *absent* rather than zero; and the copy is the neutral
   wording, true in both futures, carrying the D8 custody sentence including
   *"anyone who calls that custodial is right"*.

2. **`$PUMP` is Token-2022**, not SPL Token (`references.md`, read 2026-09-01).
   A reserve balance read through an associated-token address derived with the
   SPL Token program id resolves to a different, empty account — **a confident
   zero on the page that matters most**. `readBalance` filters by mint through
   `getTokenAccountsByOwner` and derives no address at all.

3. **`settle_issuance` calls `survivors.take` only when `minted`.** Past 4,000
   the issuance still fires and emits `piece_id = u16::MAX`, consuming no
   survivor. A replay that takes on every event runs one ahead of the chain from
   that hour onward. Unreachable at 51 issuances on devnet; a live defect at
   4,000, which is the one hour nobody would be watching a replay.

4. **The schedule is anchored on chain**, so the hosting question is not about
   cron precision at all. This inverted the entire batch — see D22.

5. **The noindex triple** already existed in three places and the placeholder's
   `outputDirectory: "public"` would have served an empty directory after the
   Next migration.

6. **`app/**/*.tsx` was already in the lexicon corpus.** B0 anticipated this
   batch. `README.md` was not, and now is.

7. **`period_seconds` is written by `initialize` (D15)**, so the cranker reads
   its schedule from the config account rather than a local file, and checks it
   against a literal.

## 3. The honest recommendation

**Batch 1: build it as asked.** Done, and it found two defects that were not in
the brief — the `minted` gate above, and a retry loop that treated Helius'
`-32429` rate limit as fatal because the error arrives as JSON-RPC inside an
HTTP 200.

**Batch 2: build the process, do not buy the host.** The evaluation is worth
having now; the purchase is not ours to make, and CLAUDE.md is explicit that
anything paid is paid by a route the owner decides and this repository never
records. `flyctl` and `vercel` both report no local credentials.

**Batch 3: build it, and say the reserve does not exist.** The alternative — a
`0.000000 $PUMP` next to the word "reserve" — is not a smaller version of the
feature. It is a false one, on the number this project is ultimately judged by.
